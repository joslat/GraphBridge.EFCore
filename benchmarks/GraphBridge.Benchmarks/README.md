# Optional GraphBridge performance evidence

This executable implements the node and relationship workloads described below. It is outside the runtime package and has no BenchmarkDotNet or new third-party dependency. The complete specified matrix passes hosted run 38123594691; measured results and durable raw evidence (maintainer-local record) record the environment and limitations. No timing target or production SLO is claimed.

Execution must go through the repository's resource-supervised Community-fixture runner. The executable requires `GRAPHBRIDGE_BENCHMARKS=1`, `GRAPHBRIDGE_BENCHMARK_GUARDED=1`, the generated integration environment, exact random Compose identity/marker, `bolt://127.0.0.1:17687`, database `neo4j`, and a verified Neo4j **2026.09.0 Community** server. It does not accept an arbitrary connection string, start Docker, or accept an Enterprise license. The caller must verify Docker ownership and monitor the 5 GiB host reserve throughout execution; fresh explicitly opted-in GitHub-hosted runners use the existing 2 GiB policy. Directly setting the guard variable is not a substitute for that runner.

Restore/build and execution are coordinated by the primary agent. The pure tests live in `../GraphBridge.Benchmarks.Tests`; they exercise percentile mathematics and bounded options without a database. `--help` is offline. The optional runner is [`eng/scripts/Run-Benchmarks.ps1`](../../eng/scripts/Run-Benchmarks.ps1), with offline synthetic policy checks in [`Test-BenchmarkPolicy.ps1`](../../eng/scripts/Test-BenchmarkPolicy.ps1). The full hosted run passes 76 C# tests, 60 runner policy assertions and live execution; see the results record for exact coverage.

After separately building the selected configuration and starting the existing owned Community fixture, invoke the runner with PowerShell 7+:

```powershell
# Explicit small acceptance smoke; does not establish the larger performance matrix.
pwsh eng/scripts/Run-Benchmarks.ps1 -Sizes '100' -EdgeSizes '1,100' -Writes '1' -Samples 2 -Warmups 0 -Configuration Release -TimeoutMinutes 10

# Full selected methodology, subject to resource availability and a finite duration.
pwsh eng/scripts/Run-Benchmarks.ps1 -Sizes '1,100,10000,100000' -EdgeSizes '1,100,10000' -Writes '1,100,1000' -Samples 20 -Warmups 3 -Configuration Release -TimeoutMinutes 60
```

Runner parameters also include `-FetchSize` and `-Seed`. Configuration defaults to Release and accepts Debug for explicit debugging evidence. Timeout defaults to 30 minutes and accepts 1–60. It invokes the existing DLL directly, with no restore/build/MSBuild subprocess. Its single argument vector uses `ProcessStartInfo.ArgumentList`; generated fixture values override stale values only inside the child environment, leaving parent variables untouched.

The runner verifies the exact pinned image, selected Compose/disposable labels, healthy running state, both loopback bindings, 1536 MiB container RAM limit, one CPU limit and disposable data/log tmpfs configuration. It checks the existing shared-memory preflight before launch, records an initial available-memory sample, then samples every five seconds and aborts below the reserve plus 256 MiB monitoring headroom. It enforces its duration and kills/waits for only its own child tree on failure. If memory cannot be measured or remains below reserve afterward, it revalidates and stops only the selected now-idle fixture. That fixture then requires dedicated teardown/recreation. Interrupted processes can leave synthetic run data; the runner does not disguise forced termination as successful graph cleanup. Process/output finalization is checked before reporting success; cleanup errors mark runner provenance as failed.

A benchmark operation lock prevents simultaneous benchmark runners. Other test/build entry points do not participate in that lock; primary-agent coordination still serializes shared database work. The runner never enumerates credentials or serializes whole Docker inspections. It creates `.artifacts/benchmarks/<UTC>-<GUID>/` with safe `runner.json` provenance, stream-copied stdout/stderr logs, memory samples, and the harness's `data/` artifacts. Provenance includes actual checkout commit/dirty flag, benchmark DLL hash, host/CPU observations, selected node/edge/write sizes and allowlisted container settings. A successful child exit must also provide `completion.json` and `edge-completion.json` with matching selected matrices and complete separate plan/protocol coverage; timeouts, low-memory interruption and missing completion evidence fail the runner.

All arguments use `--name=value`. A smoke matrix is `--sizes=100 --edge-sizes=1,100 --writes=1 --samples=2 --warmups=0`. This proves only its selected cells; it cannot close one-node, 10k/100k node, 10k edge or larger write acceptance. The full matrix retains the architecture's one-node case alongside the implementation blueprint's 100/10k/100k node cases and the architecture's 1/100/10k edge cases. The full matrix intentionally performs many individual commands; batch sizes are EF SaveChanges transaction sizes, **not an UNWIND optimization silently applied only to the direct control**.

## Equivalent operations and explicit boundaries

Read workloads stream all selected run-scoped nodes ordered by `Ordinal`. Full reads construct the same five-property `BenchmarkPerson`; scalar reads return the same ordinal values. Every value, count and order is checked, not just a checksum. Direct reads and provider reads use selected-database auto-commit sessions, fully exhaust their cursors and dispose sessions. Both use one real shared driver/pool, equal fetch size and the same API observer. Each EF operation gets a fresh context. TrackAll, AsNoTracking and AsNoTrackingWithIdentityResolution are separate cells; scalar projections track no entities. The direct arm is an untracked object/scalar baseline; it does not pretend to reproduce EF's identity map or snapshots. Unique keys occur once, so the identity-resolution cell measures its overhead but does not exercise duplicate-key reuse.

Writes run each batch size against each selected background graph size. Both arms create, update and delete **independent versioned nodes**, using supplied stable Guid keys and one atomic transaction. Each transaction observes the actual node uniqueness constraint. Updates/deletes acquire a key-preserving node write lock, then check the original numeric version; updates increment it and deletion is plain `DELETE`. Every mutation must affect exactly one node. Neither arm uses managed retry, UNWIND write batching, DETACH DELETE or a transaction per row. EF owns all state on the provider side. Entity construction is outside timing for both; EF context creation, attachment/change detection, SaveChanges and acceptance are inside. Direct transaction/session setup and post-commit version publication are inside its measurement. Those EF services are real additional semantics, not a second hand-written tracker in the control.

A fresh administrative read verifies every committed property/version/count after each write, outside timing. A deliberate stale-version second update verifies whole-batch rollback for both arms before completion. Setup and cleanup are outside measured samples. Dataset/operation IDs are random; keys preserve 96 random bits with an ordinal suffix. Seeding and cleanup use at most 1000 nodes per command, cleanup has a finite maximum, and cleanup fails on unexpected relationships. The fixture-owned uniqueness constraint remains until fixture teardown, matching other integration schema. No graph-wide deletion or unrelated schema drop occurs.

After the node matrix and cleanup, the runner executes a separate **identified-edge read matrix** for every selected edge count. Each count has eight equivalent full/scalar cases: direct driver plus EF tracked, no-tracking and identity-resolution modes. Every physical relationship has its own stable application Guid; up to ten sources and one hundred targets are reused, with parallel edges above one hundred relationships. The direct control preserves the provider's mapped endpoint matching, canonical required IDs, bounded type-global identity check and three observed uniqueness constraints. Full results validate every ID, directed endpoint and payload; scalar results validate each ordinal, with required key/cardinality decoding retained. Raw physical inventory additionally checks that the FK values were not copied onto relationship properties.

The edge workload has its own compilation/allocation/first-row/total timings, protocol observations and actual EXPLAIN/PROFILE plans. EF remains the sole state owner. Endpoint and edge fixture seeding is outside timing and is **not an edge write benchmark**. Each edge run deletes only its random run-scoped relationships, then its endpoints with plain restrictive deletion, and verifies cleanup before completing. The parent completion file is written only after both workloads succeed, persist evidence and finish cleanup. There is no native-reference, association-edge, Include or edge-write performance claim; those remain optional workload extensions rather than substitutes for the required node and edge read evidence.

## Timing and allocation interpretation

Each case records one `first-observed` sample, separate `warmup` samples and measured `warm` samples. A deterministic shuffle changes arm order on each iteration. Model initialization is timed separately before queries. EF 10.0.12 `QueryCompilationStarting`/`QueryExecutionPlanned` events record actual compilation spans and counts; cached cases correctly report zero. This avoids falsely calling every new DbContext a cold compilation. First-observed is **not** a cold-process/server/page-cache/TLS measurement: connectivity, schema and seed verification have already run, and query caches are reused between graph sizes. Use separate supervised processes for independent replicates; raw evidence records this limitation.

Read samples include time to first shaped row and total time through enumeration and disposal. The acceptance-only EF `ChangeTracker.Entries()` scan triggers change detection, so its measured interval and allocations are subtracted; context disposal remains included. Total otherwise includes server, driver, EF shaping, per-row validation, observer overhead and GC; it is not a pure network or isolated materialization benchmark. Compilation duration is separately reported but subtracting it still leaves mixed execution/materialization work. Isolated materializer CPU attribution is an optional profiling follow-up, not an additional release condition in the original methodology. Warm samples eliminate the initial compilation where the event count confirms cache reuse.

Allocations use `GC.GetTotalAllocatedBytes(precise: true)` around each operation, **process-wide**, because asynchronous work changes threads. They include background driver activity and observer/validation overhead; they are not thread-local application allocations or retained heap size. No forced GC is inserted between samples. Percentiles use empirical nearest rank. With 20 samples p95/p99 have little tail resolution; raw observations are always published, and larger sample counts require resource/time budgeting. There is no invented performance threshold.

## Protocol accounting and source evidence

`InstrumentedDriver` delegates the real public `IDriver`/session/transaction/cursor interfaces through `DispatchProxy` and records actual public method invocations. Both arms have that overhead. `RunAsync`, `FetchAsync`, `ConsumeAsync`, begin, commit and explicit rollback counts are emitted **as application API calls only**. A buffered `FetchAsync` need not use the network; one Run may pipeline several messages and records may require multiple pulls. These counts cannot be relabeled Bolt round trips. Implicit cleanup rollback messages are not inferred from Dispose.

Pinned Driver **6.3.0** source inspection found (rechecked for **6.4.0** on 2026-10-24: `INeo4jLogger`, `IMetrics`, `IResultSummary`, `IQueryProfile`, `IPlan`, `ChunkWriter`, `ResponsePipeline` and the prefixing loggers are unchanged; `SocketClient` only gains `SystemReportsDead()`):

- [`INeo4jLogger`](https://github.com/neo4j/neo4j-dotnet-driver/blob/6.3.0/Neo4j.Driver/Neo4j.Driver/Public/INeo4jLogger.cs) offers unstructured debug/trace Bolt message logging. The observer is disabled during all timed samples and enabled only for separate, fully consumed warm executions of each matrix case. It reads exact message types and templates without formatting or retaining argument values, query text, exceptions or hexadecimal buffers.
- [`IMetrics`](https://github.com/neo4j/neo4j-dotnet-driver/blob/6.3.0/Neo4j.Driver/Neo4j.Driver/Internal/Metrics/IMetrics.cs) is internal and exposes connection-pool activity, not protocol round trips.
- [`IResultSummary.QueryProfile`](https://github.com/neo4j/neo4j-dotnet-driver/blob/6.3.0/Neo4j.Driver/Neo4j.Driver/Public/Summary/IResultSummary.cs) and [`IQueryProfile`](https://github.com/neo4j/neo4j-dotnet-driver/blob/6.3.0/Neo4j.Driver/Neo4j.Driver/Public/Summary/IQueryProfile.cs) are the actual non-obsolete PROFILE APIs used here; statistics may be null when the server omits them.
- `IResultSummary.HasPlan`/`Plan` and `IPlan` supply the separate EXPLAIN tree. The installed Driver 6.3.0 XML contract confirms these APIs. EXPLAIN must return no rows, no profile and no graph/system update counters; a missing plan fails evidence collection.

`BoltProtocolObservation` counts **completed serial Bolt batch exchanges**, a bounded protocol round-trip definition: one outgoing flush of one or more requests followed by all matching terminal responses, before another flush. `RUN` plus `PULL` can share one exchange; records do not count as separate exchanges. Pinned [SocketClient](https://github.com/neo4j/neo4j-dotnet-driver/blob/4ed413b01906c5d1682c62a3ee3c982cb28f99cd/Neo4j.Driver/Neo4j.Driver/Internal/Connector/SocketClient.cs), [ChunkWriter](https://github.com/neo4j/neo4j-dotnet-driver/blob/4ed413b01906c5d1682c62a3ee3c982cb28f99cd/Neo4j.Driver/Neo4j.Driver/Internal/IO/ChunkWriter.cs) and [ResponsePipeline](https://github.com/neo4j/neo4j-dotnet-driver/blob/4ed413b01906c5d1682c62a3ee3c982cb28f99cd/Neo4j.Driver/Neo4j.Driver/Internal/MessageHandling/ResponsePipeline.cs) establish these boundaries. The observer rejects overlapping, incomplete, multi-connection, authentication and unknown event sequences instead of guessing. This does not count TCP packets or measure physical RTT latency. Logging builds transient buffers inside the driver, which is why these observations are excluded from timing/allocation samples. The exact informational version `6.4.0+4ed413b01906c5d1682c62a3ee3c982cb28f99cd` is required; the installed assembly version is 6.4.12.0. On 6.3.0, offline tests and the complete specified live matrix passed, with all 128 protocol observations valid in run 38123594691; the live matrix has not been re-run on 6.4.0.

## Artifacts and provenance

PROFILE read collection explicitly fetches and counts every result row before requesting its summary. `ConsumeAsync` alone discards unread records; the first full run failed at 10,000 rows when PROFILE results crossed the driver's fetch boundary. A shared cursor helper checks exact cardinality without retaining records. The hosted `profile` mode selects 10,000 nodes/edges with two samples for regression diagnosis; smoke uses fetch size 16 so even 100-row reads cross a fetch boundary. This changes untimed plan collection only; the measured workload still fully enumerates its results.

- `environment.json`: exact observed server/edition, runtime/assemblies, OS/architecture/CPU count, options and model initialization. The guarded runner supplies `GRAPHBRIDGE_BENCHMARK_COMMIT`, `_IMAGE`, `_CPU`, `_MEMORY`, `_DOCKER_LIMITS`; absent fields are explicitly marked missing, never invented.
- `raw-samples.json`: every measured/warmup/first-observed sample, counts, timing and process allocations.
- `summary.json`: warm-only p50/p95/p99/min/max and allocations by matrix cell.
- `protocol-samples.json`: one separate untimed observation per matrix case, with completed serial exchanges, request/batch/response counts and explicit validity. Invalid evidence prevents completion.
- `profiles.json`: real server PROFILE trees for each actual captured direct/provider read command with the same parameters, outside timed samples. Representative single-node create/lock/update/delete direct-control statements are profiled in a rolled-back transaction at each graph size. These are labeled honestly; they are not profiles of every EF write batch.
- `explanations.json`: real server EXPLAIN trees for the same commands and exact same parameter objects used by PROFILE. Each representative write is explained immediately before its PROFILE inside the same rollback transaction, so the existing create/update/delete sequence and original versions remain unchanged. EXPLAIN supplies planning evidence, not execution metrics. Completion requires both plan kinds for eight read cases and five representative write steps (including both locks) per selected graph size. Partial plan evidence is retained on failure.
- `edge-environment.json`, `edge-raw-samples.json`, `edge-summary.json`, `edge-protocol-samples.json`, `edge-plans.json`: separate identified-edge read evidence. Plans retain an explicit EXPLAIN/PROFILE mode; environment describes topology and the read-equivalence boundary. General host/server/build provenance remains in `environment.json` and `runner.json`.
- `edge-completion.json` / `edge-failure.json`: the edge workload's independent result after its owned cleanup and evidence persistence. Passing edges alone does not imply parent completion.
- `completion.json`: written only after both selected matrices, protocol/plan coverage, node rollback checks, owned cleanup and raw evidence persistence succeed. Its `Nodes` and `Edges` sections keep size/count coverage separate. Partial runs must not be presented as completion.
- `failure.json`: safe stage, exception type names, bounded Neo4j error codes, remaining random run IDs and cleanup failures. Original failures survive secondary cleanup errors; all remaining cleanup and raw persistence are attempted. Exception messages and credentials are omitted.

The harness never serializes credentials, auth tokens or captured parameter dictionaries. Cypher text and EXPLAIN/PROFILE arguments describe synthetic benchmark data only. Do not publish `.fixture.env` or raw Docker environment inspection. The expanded Release checkpoint passes 76 offline C# tests and 60 runner policy assertions. The guarded local smoke covers 1/100 nodes and 1/100 identified edges, with batch-one writes, real EXPLAIN/PROFILE and valid separate protocol evidence. See the implementation tracker for raw artifact locations and exact limits. The full matrix has passed and its independently audited raw evidence closes the specified performance gate; the earlier smoke remains narrower historical evidence. The manual `Owned Neo4j benchmark evidence` workflow offers smoke, profile-regression and full modes with retained artifacts and unconditional owned-fixture teardown.

The optional focused allocation investigation (maintainer-local record) reuses the original 100k-node read path but has a separate completion contract. It collects warm-window GC allocation stacks under the same resource/ownership supervisor; it does not stand in for the full matrix.
# Focused experiments

## Bulk node comparison

`Run-Benchmarks.ps1 -Bulk -Sizes 1 -EdgeSizes 1 -Writes '1,100,1000' -Samples 6 -Warmups 2` selects a separate owned-fixture experiment after a successful Release build. `Writes` chooses actual batch sizes; the graph/edge sizes are required placeholders. Start the repository-owned fixture beforehand and remove it in `finally`. The existing memory, timeout, provenance and process-ownership supervisor remains active. No GitHub Actions run is needed.

This mode compares a full tracked EF read/save, actual `ExecuteUpdateAsync`/`ExecuteDeleteAsync`, and a model-specific native batch. Every timed sample starts from identical fresh seeded values and receives a complete direct-driver read afterwards. Backend order is randomized per iteration using the retained seed. Model setup, seeding, verification and cleanup are excluded from timings; first-observed/warmup samples remain separately identified. Public-driver observer overhead and process-wide allocation are included for every backend. Separate untimed protocol probes count Bolt exchanges, including metadata, cursor and transaction traffic.

The native control checks the key constraint, expected version/count and transaction result on this known fixture; it does not implement all provider model/conversion/snapshot guards. Both updates assign a constant name, increment an integer field and advance versions. Bulk does not refresh tracked objects; the tracked arm does. Command text must remain stable across samples, warm EF compilations must be zero and actual driver call counts must match the implemented paths. `bulk-completion.json` is written only after the selected matrix and cleanup pass. This mode does not benchmark relationship throughput or establish production latency percentiles.

## Offline query preparation

`dotnet benchmarks/GraphBridge.Benchmarks/bin/Release/net10.0/GraphBridge.Benchmarks.dll --query-preparation` runs a fixed, transport-rejecting preparation experiment without Neo4j. It emits raw JSON for ten warm batches, changing values and list lengths while checking one EF compilation and stable Cypher. See the method and retained results (maintainer-local record). This mode measures synchronous query preparation only; normal live benchmarks retain their guarded-fixture requirements.
